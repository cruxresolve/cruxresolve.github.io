GhostTune v1.0 Is Submitted — and GhostBridge Is Growing Beyond RS232

GhostTune has reached a major milestone: v1.0 has been submitted to Apple for App Store review. At the same time, GhostBridge is beginning its next chapter with a broader multi-transport architecture.

GhostTune has reached a milestone I’ve been working toward for a long time: GhostTune v1.0 has been submitted to Apple for App Store review.

That does not mean it is approved yet, and I don’t want to blur that distinction. But it does mean the first production release has moved out of development and validation and into Apple’s review process.

At the same time, GhostBridge is beginning its next chapter.

The current GhostBridge v1.0 (GB-01) is still the product that exists today: a local WiFi-to-RS232 TCP bridge, built and verified around the GhostTune + MicroSquirt workflow.

But GhostBridge v2.0 — internally GB-02 — is being designed to become something much broader.

What GhostTune v1.0 Actually Supports

One thing I’ve tried to be careful about throughout this project is separating what is planned from what has actually been verified.

The current GhostTune release is validated around:

  • MicroSquirt hardware
  • MS2/Extra 3.4.4
  • local WiFi communication
  • live ECU data
  • VE, ignition, and AFR table editing
  • temporary ECU writes
  • permanent burns
  • tune-file management and backups
  • diagnostics and guided workflows

There are other ECU platforms I want GhostTune to support, but I’m not going to call them supported simply because they are technically interesting or theoretically compatible.

Each platform has to earn that status through real communication testing, write verification, burn behavior, reconnect behavior, failure handling, and recovery testing.

That same philosophy is now influencing how I’m approaching GhostBridge v2.0.

GhostBridge v1.0 Is Not Going Away

GhostBridge v1.0, also known as GB-01, is intentionally simple.

It creates its own local WiFi network and transparently relays data between a TCP client and an RS232 device.

For GhostTune, that means the iPhone or iPad can communicate with a supported ECU without a physical cable connected to the Apple device.

But GhostBridge itself does not actually need to understand an ECU.

It does not know what a VE table is. It does not know what ignition timing means. It does not know whether the bytes passing through it belong to an engine controller, a piece of industrial equipment, a test instrument, or something else entirely.

That distinction became increasingly important as I worked on the next version.

Transport Is Not Protocol

One of the central design rules behind GhostBridge v2.0 is:

Transport is not protocol.

A wired interface such as RS232, RS485, CAN, TTL UART, or USB defines how information physically moves.

The application protocol defines what those bytes or frames mean.

Those are not the same thing.

That sounds obvious when written down, but treating them as separate layers changes the entire architecture of the product.

Rather than designing GB-02 as “a box that talks to a specific ECU,” the goal is to build a platform that can move bytes and frames between WiFi clients and several different physical interfaces.

The software on the other end remains responsible for understanding the device. That could be GhostTune. It could also be completely different software talking to completely different hardware.

GhostBridge v2.0

GB-02 is currently in development as the next-generation GhostBridge platform.

The present design direction includes planned support for interfaces such as:

  • RS232
  • TTL UART
  • RS485
  • CAN / CAN-FD
  • USB serial / USB host
  • a universal breakout-harness architecture for transport-specific connections

Those are development targets, not shipping feature claims.

The hardware, firmware, protection circuitry, connector system, PCB layout, and factory-test strategy are still being engineered and qualified.

That distinction matters.

I would rather publish a shorter list of things that actually work than a longer list of things that only exist in marketing copy.

Why Build a Universal Interface?

GB-01 worked because its job was narrow.

RS232 in one side. WiFi on the other.

That simplicity is one of its strengths.

But once I started thinking about broader hardware support, simply adding more connectors to the enclosure stopped making sense.

Different devices need different electrical interfaces. Some use differential signaling. Some use single-ended serial. Some use CAN. Some may need USB.

So GB-02 is being designed around a universal I/O connection and a breakout harness that can adapt the main unit to the interface required by the connected device.

Internally, I’ve jokingly referred to that breakout as the “octopus cable.”

The final name may be more dignified.

Maybe.

The Same Safety Philosophy

The architecture is broader, but the engineering philosophy has not changed.

For GhostTune, I’ve always treated communication with a live ECU as something that deserves deterministic behavior.

Pause polling. Control the connection. Perform the operation. Verify the response. Read the result back. Resume only when the state is known.

GB-02 is being approached the same way.

The objective is not simply to make something that can move data.

It is to make something whose behavior can be understood, tested, and trusted.

That means protection circuitry matters. Power architecture matters. Connector strain matters. PCB routing matters. Factory test access matters.

And each transport has to be tested as its own electrical system rather than treated as another label on a feature list.

What Happens Next

For GhostTune, the immediate milestone is now outside my hands for a moment: Apple’s App Store review process.

Development does not stop there.

Additional ECU support remains part of the roadmap, including further MegaSquirt-family work and Teensy-based platforms.

For GhostBridge, development continues on GB-02 while GB-01 remains the currently available RS232 product.

The two projects are also becoming more independent from each other.

GhostTune can grow into a tuning platform that supports additional hardware.

GhostBridge can grow into a general-purpose wireless transport interface that is useful well beyond GhostTune.

They work well together, but neither needs to exist solely for the other.

That is probably the biggest architectural change since I started building this system.

What began as “how do I tune this ECU from my phone?” is slowly becoming two separate products:

software that understands machines, and hardware that connects to them.

And that feels like the right direction.
